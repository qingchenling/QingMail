## 1. 一页速览 ★

QingMail 是 Linux 原生邮件客户端：Rust + GPUI Kit + gpui-kit-material，优先 Arch / Hyprland / 原生 Wayland；不使用 Electron / WebView；通用 IMAP/SMTP 优先，OAuth 最早 P4。

当前状态（2026-11-17，P3-006a）：

| 项目 | 现状 |
| --- | --- |
| 阶段 | P0/P1 已验收；P2 已完成；P3-005 按需正文与附件下载已实现；真实多账号/断网兼容集中验收留 P3-007 |
| 工作区 | 7 个 crate；SQLite schema14；具体文件/行数以源码为准 |
| 测试 | 日常只运行相关过滤测试，P3/P4整阶段收口才全量；历史P3-004全量196项；协议使用本机TLS假服务器 |
| 已贯通 | 添加账号→手动/自动收信→搜索→阅读/回复/转发→标记/归档/删除→写信/草稿→确认发送→已发送副本→发送任务→设置 |
| 当前调整 | 006a服务器草稿目录识别、原件保留与显式转换；006双向上传/共同基线/冲突仍未完成 |

crate 结构与依赖方向（依赖只能向下）：

```text
┌──────────────────────────────────────────────────────────────┐
│ mail-ui       GPUI 窗口：首页/账号/邮箱/阅读/写信/发送记录      │
└───────────────▲──────────────────────────▲───────────────────┘
                │                          │
┌───────────────┴──────────┐   ┌───────────┴───────────────────┐
│ mail-daemon              │   │ mail-service                  │
│ 生命周期/存储线程/发送协调 │   │ IMAP/SMTP/凭据/已发送副本       │
│ 单实例/托盘               │   │ （不依赖 UI，不访问 SQLite）    │
└───────▲──────────▲───────┘   └───────────▲───────────────────┘
        │          │                       │
┌───────┴──────┐ ┌─┴───────────────────────┴───────────────────┐
│ mail-storage │ │ mail-content                                 │
│ SQLite/对象   │ │ 不可信 MIME→受控阅读树；受控富文本 Draft      │
└───────▲──────┘ └───────────────────────▲───────────────────┘
        │                                │
┌───────┴────────────────────────────────┴───────────────────┐
│ mail-core：领域模型与操作语义（无任何内部依赖）               │
│ mail-protocol：IPC v1 / DTO（依赖 core/content）                      │
└──────────────────────────────────────────────────────────────┘
```

三条不可打破的铁律：

1. **发送只能经状态机**：任何发送/重发/停止都必须走 `mail-storage` 的 `send_tasks` 状态机；不得在 UI 或协调器里直接改状态，不得自动重发（[ADR-0005](adr/0005-发送状态机禁止自动重发.md)）。
2. **SQLite 单写者**：数据库连接只存在于 `mail-daemon` 的存储线程；UI/网络线程只能发请求。
3. **不可信输入先解析**：邮件正文只经 `mail-content` 变成受控树/副本；不手写 HTML 正则，不直接渲染原始 HTML。

## 2. 分层架构与依赖规则 ◆

### 2.1 crate 职责与依赖

| crate | 职责 | 允许依赖 | 明确禁止 |
| --- | --- | --- | --- |
| `mail-core` | 领域类型：账号、信箱四元组、文件夹、草稿头、`SendState`、发送快照 | 无 | 依赖 GPUI、存储、网络 |
| `mail-protocol` | IPC v1、共享 DTO、有界传输 | `mail-core`、`mail-content` | 密码、任意文件路径、邮件网络逻辑 |
| `mail-content` | 不可信 MIME → 受控 `Document`；`Draft` 富文本模型；浏览器副本 `CopyStore` | 仅第三方解析/清理库 | 依赖 UI、网络、SQLite、`mail-core` |
| `mail-storage` | SQLite schema/迁移、私有对象、草稿/附件/发送任务、缓存、持久请求及凭据引用 | `mail-core`、`mail-content`、`mail-protocol` | 发起网络、依赖 GPUI、暴露连接给 UI |
| `mail-service` | IMAP/SMTP 协议适配、Secret Service、发送前校验、APPEND 副本 | `mail-core`（生产） | 依赖 `mail-storage`（仅 dev-dependencies 供测试）、保存密码明文 |
| `mail-daemon` | 独立后台生命周期、唯一存储线程、邮件业务/发送协调、会话、托盘 | 以上全部 + zbus/rustix | 依赖 GPUI、在 UI 线程做网络 |
| `mail-ui` | GPUI 窗口、输入、渲染、探针 | 以上全部 + GPUI 栈 | 直接打开 SQLite、直接做协议 |

> `mail-ui` 虽然依赖 `mail-storage`/`mail-service`，但只使用**类型与函数**：数据库句柄与网络调用分别被 `StorageClient` 和 `mail-service` 封装，不越过边界。

### 2.2 数据与网络边界

```text
用户操作
  │
  ├─ 本地读/写 ──► StorageClient（请求队列）──► 存储线程 ──► SQLite + objects/
  │
  ├─ 网络 ──────► mail-service（临时连接）──► IMAP / SMTP
  │                 ▲
  │                 └─ 凭据只在调用瞬间从 Secret Service 读取（Zeroizing<String>）
  │
  └─ 渲染 ──────► mail-content 的受控 Document / Draft → GPUI
```

- 正式数据目录：`XDG_DATA_HOME/qingmail`（或 `~/.local/share/qingmail`）；配置/缓存分目录；运行目录不回退 `/tmp`（[paths.rs](../crates/mail-storage/src/paths.rs)）。
- 主动网络操作使用临时连接，操作结束 `LOGOUT`/`QUIT`，不做连接池。每账号最多一条独立只读 IDLE 会话（当前最多15秒后关闭重建），失败或不支持时60秒轮询；启动立即收信。主动 IMAP 最多两个、同账号串行，阅读优先。
- 原始 MIME 作为不可变对象保留，阅读树与 HTML 都是可重建的派生结果。

## 4. 逐 crate 说明

### 4.1 `mail-core` ◇

纯领域模型，无依赖、无 I/O。关键类型：

- `AccountId`/`DraftId`/`AttachmentId`/`SendTaskId`：不透明字符串 ID，稳定性由存储层保证。
- `MailUid`：`(account, folder_id, uidvalidity, uid)` 四元组，定位一封远端邮件；**不要用 Message-ID 代替**。
- `AccountSettings`/`ServerSettings`/`ConnectionSecurity`：非秘密配置；枚举只允许 `Tls`/`StartTls`，没有“跳过证书验证”选项。
- `FolderBatch`/`RemoteFolder`/`FolderCache`/`CachedMessage`：同步与缓存快照。
- `SendState`、`SmtpOutcome`、`ResendAuthorization`：发送语义；`ResendAuthorization::UserConfirmed` 是“重发必须用户确认”的类型级提醒。
- `OutgoingSnapshot`/`OutgoingAttachment`/`AttachmentInfo`：冻结的发送快照。

新增业务语义先判断是否属于领域模型：只放**与实现无关**的类型和规则，不放 SQL、协议字符串或 UI 状态。

### 4.2 `mail-protocol` ◇

P0–P2 为进程内调用。P3 已冻结 `PROTOCOL_VERSION = 1`，提供共享 DTO、控制帧和二进制资源帧边界。正式 GUI 已使用 IPC，后台处理账号检查/安全提交、存储、收发、阅读解析与安全副本、托盘；未实现的 P3 后续能力仍返回 Unsupported。旧进程内适配仅供隔离诊断，详见 [P3 当前状态](P3-当前状态与剩余工作.md)。

### 4.3 `mail-content` ◆

输入是不可信字节，输出是可重建的受控结果：

1. `parse` 用 `mail-parser`（限制深度 32、部件 256、编码嵌套 4、总大小 8 MiB）。
2. 附件逐个解码并保留 `name/media_type/content_id`；重复 Content-ID 有明确警告并阻止歧义映射。
3. 内嵌图片经 `image` 重新编码为 PNG（每张 2 MiB、总数 32、总预算 8 MiB）。
4. HTML 经 `ammonia` 清理、CSS 经允许列表过滤后进入 `Document`（`Element`/`Node` 树）或浏览器副本。
5. 纯文本、HTML、损坏 MIME 都有降级路径与 `warnings`；从不 panic、从不把原始 HTML 直出。

`Draft` 是写信的**唯一**正文模型：文本 + 每 scalar 属性（粗体/斜体/链接/块类型），不存 HTML；`html()`/`plain_export()` 是导出，不是存储格式。索引语义是 Unicode scalar，UI 边界用 UTF-8 字节（`scalar_range` 负责换算）。

`CopyStore` 与 `DraftStore` 都用目录 fd 锚定、单写者锁、临时文件 + fsync + 原子替换；浏览器副本默认 24 小时清理。

### 4.4 `mail-storage` ◆◆

**所有权**：每个数据目录一个写者（`PrivateDir::lock`）；`Store` 只能在存储线程中创建和使用。

**文件布局**：

```text
<data>/state.sqlite3          主库（application_id + user_version=6）
<data>/objects/<id>           不可变正文/附件对象（sha256 校验、0600）
<data>/migration-v<N>-*.sqlite3  迁移前备份
<data>/writer.lock            写者锁
```

**数据模型**（schema 汇总）：

| 表 | 作用 |
| --- | --- |
| `accounts` | 远程账号；`kind='local'` 是本地草稿空间（唯一） |
| `folders` / `remote_folders` | 已 EXAMINE 的文件夹 / LIST 目录（NoSelect 无 UIDVALIDITY） |
| `messages` / `folder_messages` | 邮件头与四元组定位，多文件夹关联独立 |
| `folder_sync` / `catalog_sync` | 同步时间、90 天起点、是否还有更多 |
| `objects` | 不可变对象（body/attachment），sha256 |
| `attachments` / `draft_attachments` / `task_attachments` | 附件与草稿/任务引用 |
| `drafts` | 草稿头 + revision + 正文对象 |
| `send_tasks` | 发送状态机、冻结快照、`resend_of`、副本位置 |
| `local_editor` | 单编辑窗口记忆的当前草稿 |
| `message_bodies` | 旧完整 MIME 缓存与≤8MiB结构异常回退 |
| `server_draft_folders` / `server_draft_sources` | schema14：显式目录选择、原始MIME对象、内容哈希、转换副本与转换时本地版本；尚非上传共同基线 |
| `message_structures` / `part_resources` | 不可变MIME清单、分段对象关联与访问时间（schema13）；预算/淘汰留007 |

**发送状态机**（唯一写入口）：

```text
pending ──begin_smtp──► sending ──finish_smtp(Accepted)────► copy_pending
   │                       │                                      │
   │                       ├─finish_smtp(DefinitelyRejected)────► failed
   │                       └─finish_smtp(Uncertain)─────────────► uncertain
   │
   └─cancel_pending──► failed

copy_pending ──finish_copy(Saved)──────────────► sent
copy_pending ──finish_copy(Failed/Uncertain)───► copy_pending（只重试副本）

failed / uncertain ──resend_task(UserConfirmed)──► 新 pending 任务（旧记录保留）
uncertain ──stop_uncertain──► uncertain（本地停止处理，不宣称撤回）
```

- `begin_smtp` 返回不可克隆的 `SmtpAttempt`；它是“可以向网络提交”的唯一许可，且写入 `sending` 成功后才返回。
- `copy_ready`/`begin_copy` 只读，不改变状态；真正落状态在 `finish_copy`。
- 恢复规则：`pending → failed(interrupted_before_submission)`、`sending → uncertain(interrupted_during_submission)`、`copy_pending` 原样保留。
- 迁移：`SCHEMA_VERSION=6`，`migrate` 在事务内按版本应用 v2…v6，失败回滚并保留私有备份。

**边界**：不在这里做网络、不在这里拼 MIME、不在这里判断 UI 文案。新增字段/表必须走 `schema-vN.sql` + `migrate` + 迁移测试。

### 4.5 `mail-service` ◆◆

**IMAP 骨架**（所有 IMAP 操作复用同一套）：

```text
connect(host,port) → Bounded（读预算/期限）→ 可选 STARTTLS → TLS
→ 登录（quoted 转义、零化缓冲）→ 命令 → response/until_done（嵌套/字面量限制）→ LOGOUT
```

- `authenticated` 是唯一登录入口；`quoted` 负责字符串转义；`response_limited` 限制单条响应与字面量；`guard_response_limit` 限制括号深度；`resolve_bounded` 为 DNS 设 10 秒上限。
- `sync::until_done` 适合只关心 tagged OK 的流程；需要取 tagged 结果码（如 `APPENDUID`）时，按 `sent.rs` 的循环写法读取 `Response::Done { status, outcome }`，**不要**改 `until_done` 的签名去迁就个别调用。
- 错误统一为 `CheckError`（Invalid/Dns/Connect/Timeout/Tls/Authentication/Protocol/Limit/EpochChanged），UI 只展示稳定文案，不展示服务器原文。

**发送侧**：

- `outgoing::prepare`：校验收件人/主题/大小/附件，构建 `plain+HTML`（`multipart/alternative` + `multipart/mixed`），Bcc 只进信封；Date/Message-ID/边界来自冻结快照，保证同一快照重建出相同字节。
- `outgoing::deliver`：一次连接、一次 `MAIL/RCPT/DATA`；返回 `Accepted`/`DefinitelyRejected`/`Uncertain` 与固定 `DeliveryDetail`；`QUIT` 失败不推翻已确认接受，之后不再重连或重发。
- `sent::save_copy`：一次 IMAP 连接内 `LIST → EXAMINE → SEARCH HEADER Message-ID → APPEND`；文件夹按“上次记录 → 常见名称（modified UTF-7 解码后匹配）→ 可选节点”选择；查重命中或查重失败都不追加；`APPENDUID` 记录 UID，无 UIDPLUS 则 UID 未知。
- 所有网络函数都接受可注入的 `TlsConnector`（`*_using`）或闭包，供本机 TLS 假服务器测试，不访问真实网络。

**凭据**：`Credentials { imap, smtp }` 不实现 `Debug/Clone`，用 `Zeroizing<String>`；`SecretService` 通过 zbus 异步连接 + 5 秒方法超时；错误分类（Unavailable/Locked/Missing/Ambiguous/Invalid/OperationFailed/Timeout）直接对应 UI 可操作提示。

### 4.6 `mail-daemon` ◆◆

**线程与通道**：

| 线程/对象 | 职责 |
| --- | --- |
| GPUI 主线程 | 渲染与事件；只通过 `StorageClient` 发请求 |
| `qingmail-storage` | 唯一持有 `Store`，顺序处理 `Request`（队列 16，满则 `try_send` 失败） |
| `qingmail-send` | 凭据 + 网络 + 副本；由 `SendCoordinator.active` 保证全局单任务 |
| `qingmail-p0-worker` | 合成 tick（生命周期证据），不联网 |
| 激活线程 | Unix socket 轮询 `Command`；持有实例锁 |
| 托盘 zbus 连接 | StatusNotifierItem + DBusMenu |

**存储请求协议**：`Request` 枚举是 UI 与数据库之间的唯一契约；新增能力 = 加一个 `Request` 变体 + `StorageClient` 方法 + 处理器分支。`receive()` 是后台线程等待回复的阻塞助手，**不得在 GPUI listener 内调用**。

**发送协调**：`SendCoordinator::confirm` 的顺序是“读密钥 → 存储线程复验并冻结 → SMTP → 写结果 → 若 CopyPending 则副本保存 → 再写结果”。`resend` 只接受 Failed/Uncertain，先取密钥再创建唯一新任务，复用同一 `run_submission`；`retry_copy` 只走副本，先 `copy_ready` 校验状态，再按冻结快照重建 MIME 并 `save_copy`，绝不经过 SMTP。

**进程入口**：`Instance::launch` 用 XDG 运行目录下的锁与 socket 实现单实例；`--status/--quit` 转发给主实例；托盘可用性由 watcher 决定。P3 才拆 daemon/IPC。

### 4.7 `mail-ui` ◆

窗口与入口：

| 窗口 | 打开方式 | 说明 |
| --- | --- | --- |
| 首页 | 默认 / 再次启动 | 过渡动画、主题切换、P0 合成列表（待正式整合） |
| 账号 | `--accounts` | 检查 → 展示 IMAP 文件夹/SMTP 结果 → 明确保存 |
| 邮箱 | `--mailbox` | 账号文件夹树、缓存列表、启动/手动同步、选信直接阅读 |
| 阅读 | `--content-demo` 或邮箱点开邮件 | `mail-content` 受控文档、CID、附件另存、远程图片授权、浏览器副本清理 |
| 写信 | 邮箱入口 / `--editor-demo` | 字段、附件、自动保存、发送预览、发送记录与副本重试 |
| 发送任务 | `--send-tasks` / 写信窗口入口 | 跨草稿任务列表、受控重发、停止处理、仅重试副本 |

生命周期：所有窗口句柄、存储、发送协调器、托盘、命令队列都在 `Lifecycle` Global 中；`tick` 每 150 ms 处理命令、回收已关闭窗口、执行“保存并退出”（等编辑保存与发送/副本写盘）。新窗口必须通过 `lifecycle` 注册与复用，不要另建 `Application` 或事件循环。

写信窗口拆分为三个文件，改动时按职责落位：`composer.rs`（编辑器/版本/保存/关闭）、`composer_fields.rs`（收件人/主题/附件）、`composer_send.rs`（预览、确认、发送记录、副本重试）。

**GPUI 三条硬约束**（违反会造成卡死或帧异常）：

1. `request_animation_frame` 只能在绘制阶段调用；事件回调用 `on_next_frame`。
2. 主题逐帧推进保持单一 pump 链，目标放在视图状态。
3. 同一实体禁止 `entity.update` 重入；listener 内联更新，仅帧回调再 `entity.update`。

开发验证入口（探针）是产品代码的一部分，但只在显式参数 + 隔离目录下运行；不要把它们接进正常路径。完整构建/运行参数见主文档 §8.3；不存在 `--demo`，mail-daemon 是库而不是独立二进制。

## 5. 关键业务流程 ◆

### 5.1 启动、激活与退出

1. `main` 解析参数 → `Instance::launch`：已有实例则把命令写入 Unix socket 并退出；否则持有锁与监听。
2. `lifecycle::start` 创建 `StorageWorker`、合成后台、`SyncEngine`、`SendCoordinator`、命令队列；托盘异步启动。
3. `lifecycle::open_main` 打开邮件主界面；默认启动、再次启动与托盘“打开”都进入邮件窗口，P0 合成首页仅由 `--home-demo` 显式打开。
4. `tick` 每 150 ms 排空命令：`Open/Editor/Reader/Accounts/Mailbox/SendTasks` 经 `cx.defer` 开窗（避免 `update_global` 重入）。
5. 退出：`--quit`/托盘 → `quitting=true` → 关闭所有编辑窗口（先刷新未保存内容）→ 等待账号保存与 `sending.active()` → `cx.quit()`。

### 5.2 添加、编辑与移除账号

1. 账号窗口收集 10 个字段，`accounts::validate` 先做纯格式校验。
2. 后台线程 `accounts::check`：IMAP `LOGIN+LIST`、SMTP `EHLO/AUTH`（**不** MAIL/RCPT/DATA/APPEND）。
3. 展示检查结果；用户明确点保存后，经 `StorageClient::add_account` 由存储线程先写 Secret Service 凭据，再插入账号。
4. 编辑已有账号：预填非密码字段，重新输入密码并检查通过后 `update_account`；账号 ID、缓存、草稿与发送任务保留，凭据覆盖同一密钥项。
5. 本地移除：先 `account_impact` 展示缓存/草稿/任务/对象字节，确认后按外键顺序删除本地数据与对象文件，再删除密钥库条目；不连接远端、不删除远端邮件；发送进行中拒绝移除。
6. 任一步失败：添加失败不写入账号；密钥写入结果不确定时保留凭据并提示，不盲目删除。

### 5.3 同步目录与邮件头

1. 邮箱窗口 `sync::folders` 取 LIST → `storage.publish_catalog` 整目录替换（失败保留旧目录）。
2. 选中文件夹后 `sync::folder`：`EXAMINE` 核对 UIDVALIDITY → `UID SEARCH SINCE 90天` → 取最新 200 个 UID → `UID FETCH (UID FLAGS HEADER)` → `storage.publish_folder`。
3. 存储层在同一事务内应用批次：epoch 变化只清除该文件夹关联；消息按 `(folders,uidvalidity,uid)` 保持稳定 ID；远端标记写入缓存。
4. 只有 `complete && !has_more` 的最近批次才对账删除 90 天内已不存在的缓存；90 天前缓存与历史批次保留。
5. 列表分页：本地缓存 200 条、每页 40；`has_more` 只表示 90 天窗口内还有更早批次。
6. 自动收信线程每 60 秒同步最多 4 个文件夹，每 5 轮刷新目录；失败退避，可暂停；窗口约每 15 秒重读当前文件夹缓存。
7. “加载更早历史”用 `SEARCH BEFORE` + UID 游标，`BatchKind::History` 只追加。

### 5.4 阅读、操作与回复/转发

1. daemon复用旧 `message_body` 缓存；无则先取大小/头部/BODYSTRUCTURE，按需缓存正文与引用CID（`parts`）；结构不支持且整封≤8MiB才有提示回退 `sync::message`。
2. `mail_content::parse_sections` 复用既有解析/安全清理→ `MailContent`；附件元信息映射为受控资源ID，用户点击后后台流式下载，前台分块另存，显示进度并允许取消。派生阅读MIME不是服务器草稿原件。
3. 远程图片默认阻止；用户对**单封**邮件授权后才 `load_remote_images_after_consent`。
4. 浏览器副本由 `CopyStore` 写单文件并设置 CSP；可立即清理或 24 小时清理。
5. 列表批量已读/未读、星标、归档、删除经持久离线队列，入库后投影“待同步”；失败/冲突/不确定在操作入口处理，不盲目重放移动。
6. 阅读窗口的“回复/全部回复/转发”（Ctrl+R / Ctrl+Shift+R / Ctrl+Shift+F）用 `reply::document` 生成收件人、主题与纯文本 Quote 引用，经存储线程创建新草稿并打开写信窗口；不覆盖当前草稿。
7. 本地搜索：邮箱窗口按关键词/发件人/有附件/文件夹或账号范围查询 SQLite；只覆盖已缓存索引，附件筛选使用已解析完整MIME或分段清单记录的附件数量；清除后恢复之前分页与选中项。
8. 同窗阅读：主窗口把既有 `Reader` 实体嵌入详情栏，复用正文/纯文本/字号/CID/附件/远程图片/浏览器副本；宽布局列表+阅读、分隔线可拖动 280–720px，窄布局返回列表；仍可“在独立窗口打开”。

### 5.5 草稿保存

1. 写信窗口把正文改动写入 `Draft` 模型，字段/附件作为同一 `DraftDocument`。
2. 自动保存带防抖；保存请求携带 `previous.revision`，冲突返回 `Conflict` 并提示，不静默覆盖。
3. 关闭前强制刷新；失败保留窗口并给出重试/另存提示（坏草稿恢复见 P2-014）。
4. 重启后按 `local_editor` 恢复最近草稿空间；账号草稿按账号隔离。
5. 工具栏“另存草稿”把字段与纯文本写入用户选择的文件；加载失败时“另存原始数据”读取对象字节，“放弃并新建草稿”只删草稿行并保留对象文件。

### 5.6 发送与已发送副本

```text
预览（不联网） → 确认 → 存储线程复验/冻结 pending → begin_smtp → sending
   → SMTP 一次提交
      ├─ Accepted → copy_pending → 重建同一 MIME → LIST/EXAMINE/SEARCH/APPEND
      │                              ├─ Saved → sent（记录副本位置）
      │                              └─ Failed/Uncertain → copy_pending（原因可操作）
      │                                   └─ 用户“重试保存副本” → 查重 → 命中则 sent
      ├─ DefinitelyRejected → failed
      └─ Uncertain → uncertain（禁止自动重发，由用户决定）
```

关键不变量：

- 预览阶段不建任务、不联网、不读密钥。
- 同一草稿版本只能获得一个初始提交许可；已有发送记录的草稿不能再提交。
- 关闭编辑窗口不取消发送；退出会等待结果写盘。
- 副本失败不推翻“服务器已接受”的事实；只重试副本。
- 重发只从任务入口由用户二次确认触发；生成新任务与新 Message-ID，旧记录保留，同一旧任务只生成一个新任务。
- 明确失败的草稿修改后可重新检查提交；相同版本、`uncertain`、`sent`、`copy_pending` 仍阻断。
- 重启不自动发送、不自动重发、不自动重试副本。

### 5.7 结果与诊断对照

| 场景 | 状态 | 用户可见 | 允许动作 |
| --- | --- | --- | --- |
| SMTP 明确拒绝 | `failed` | 发送未完成 | 修改后重新提交（新版本）；任务入口二次确认重发；查看冻结内容 |
| SMTP 不确定 | `uncertain` | 收件人可能已收到 | 任务入口二次确认重发；停止处理；查看冻结内容 |
| 已保存副本 | `sent` | 已保存副本位置 | 任务入口查看服务器副本（无 UID 时冻结内容） |
| 服务器接受、副本未存 | `copy_pending` | 勿重发 + 原因代码 | 只重试副本 |
| 副本查重命中 | `sent` | 未重复保存 | — |
| 副本结果未知 | `copy_pending` | 是否保存未知 | 重试前先查重 |

新增代码前逐条确认：

- [ ] **IMAP 连接**：用 `mail_service::accounts::authenticated`；不要新写 `TcpStream + TlsConnector + LOGIN`。
- [ ] **IMAP 命令/响应**：用 `quoted`、`response_limited`、`guard_response_limit`、`CheckError`；需要 tagged 结果码时照 `sent.rs` 的循环写，不要复制出第二套解析器。
- [ ] **SMTP**：只用 `outgoing::prepare` + `outgoing::deliver`；不要为副本、重试或探针另写 SMTP 客户端。
- [ ] **发送/重发/停止**：只调用 `outbox` 的既有方法；不要在 UI/协调器/测试里直接 `UPDATE send_tasks` 或改 `SendState`。
- [ ] **数据库**：只通过 `StorageClient` 请求；不要在 UI、网络线程、测试辅助代码里 `Connection::open`（测试除外，且应 `Store::open`）。
- [ ] **迁移**：新增 `schema-vN.sql` + `SCHEMA_VERSION` + 备份 + 往返测试；不要改旧 schema 文件（历史库仍需可迁移）。
- [ ] **MIME/正文**：解析与清理只走 `mail-content`；不要用正则处理 HTML/CSS，不要把原始 HTML 直接交给渲染/浏览器。
- [ ] **附件/正文上限**：沿用各层现有常量与校验（存储 `MAX_ATTACHMENT_BYTES`、内容 `MAX_*`、发送 `PrepareError` 分支）；不要另起第三套限额。
- [ ] **草稿正文**：只改 `Draft` 模型与 `DraftDocument`；不要把 HTML 存进 `drafts.body`。
- [ ] **错误文案**：协议层返回固定分类/代码，UI 做本地化文案；不要把服务器原文或密码写进数据库/日志。
- [ ] **窗口/线程**：新窗口经 `Lifecycle` 注册，新后台任务用 `StorageClient`/发送协调器；不要新起事件循环、独立进程或第二个存储线程。
- [ ] **单实例/托盘**：复用 `Instance`、`Tray`；不要自建 socket 或 D-Bus 名称。
- [ ] **网络期限**：新网络操作沿用 `resolve_bounded` 与阶段预算（`Bounded`/`set_timeout`），超时按“正文是否已发出”区分明确失败与不确定，不强制断开。
- [ ] **依赖**：不例行升级；需要新依赖先按 [ADR-0001](adr/0001-技术栈-rust-gpui-kit-material.md) 记录理由与版本 pin。

常见反例（都应在评审中被拒绝）：在 UI 里拼 MIME、在发送协调器里直接发 SMTP 重试、为“重试副本”新建一个状态、用 Message-ID 代替 `MailUid` 去下载正文、把密码存进账号表、把 `send_tasks` 的状态改成自由字符串。

## 7. 扩展指南（按任务查）

### A. 新增一个只读 IMAP 查询

1. 在 `mail-service` 新建/扩展函数，复用 `authenticated`、`quoted`、`response_limited`。
2. 定义明确的 `CheckError` 映射；对批量/列表设置条数与字节上限。
3. 提供 `*_using(..., &TlsConnector)` 变体，在 `sync_tests` 风格的本机 TLS 假服务器上测试命令序列与边界。
4. 若需要持久化：在 `mail-storage` 加 `Store` 方法 + `mail-daemon` 的 `Request`，再让 UI 调 `StorageClient`。
5. 回写第 3 节能力地图。

### B. 新增任务操作（重发/停止已接入，按此模式扩展）

- 已有范例：`SendCoordinator::resend`（取密钥 → `resend` 创建新任务/快照 → `begin_task` → `run_submission` → 副本）、`StorageClient::stop_uncertain`、任务窗口的二次确认。
- 新模式应保持：存储层负责状态与旧记录，协调器负责网络，UI 只负责确认与展示；不要在存储层重写状态机，不要为操作新增状态，不要自动触发。
- 已有：任务到副本/冻结内容的查看；仍缺任务列表筛选与历史浏览。

### C. 新增存储字段或表

1. 新增 `schema-vN.sql`（只追加，不改历史文件）。
2. `SCHEMA_VERSION` + `migrate` 增加 `if version < N` 分支。
3. 更新 `Store` 的读取/写入方法与类型；必要时更新 `SendTask` 等公开结构。
4. 增加迁移测试：构造旧版本库（含数据）→ 打开 → 断言列/表存在且数据保留；更新历史迁移测试的“旧布局”清理语句。
5. 涉及发送状态时，同步更新恢复规则与状态机测试。

### D. 新增 UI 窗口或入口

1. `mail-daemon::instance::Command` 加命令（如需要外部激活）。
2. `lifecycle` 记录窗口句柄、提供 `reuse_*`/`register_*`。
3. 新文件放在 `mail-ui/src/`，复用 `lifecycle::storage/sending`、`receive`、主题与组件。
4. 探针（若需要）用隔离目录环境变量，显式参数启动，不侵入正常路径。
5. 遵守 GPUI 三条约束；不要把网络/数据库调用放进 `render` 或 listener。

### E. 新增 GPUI 交互

- 动画：事件回调里 `on_next_frame`；只在绘制阶段 `request_animation_frame`。
- 主题：单一 pump 链，目标放视图状态，避免每次 render 重新开始。
- 实体更新：listener 内联改自身状态；不要在 `render` 里 `entity.update` 同一个实体。

### F. 依赖与工具链

- 版本在根 `Cargo.toml` 精确 pin；`Cargo.lock` 提交。
- 不例行升级；升级需单独一轮并跑全部门禁与原生检查。
- `rust-toolchain.toml` 在本机不切换工具链；工作区 MSRV 是声明值，不等于实测值。
