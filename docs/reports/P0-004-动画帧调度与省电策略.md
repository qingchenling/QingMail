> 历史轮次记录：下文“当前/尚未”均指本轮结束时；最新实现与待办以 [P2 当前状态与剩余工作](../P2-当前状态与剩余工作.md) 为准，不重复执行已完成工作。

- 日期：2026-11-16

## 1. 结论与产品选择

“release HUD MAX 显示 240fps，但交互仍卡顿”的主要原因是系统处于
`power-saver`，GPUI 默认的省电帧间隔为 33.333ms（约 30fps）。
实测 Intel 主题动画绘制约 2.2ms，却只提交约 28fps；仅在诊断窗口解除该限制后，
同一系统省电模式下升至约 118fps。切到系统平衡模式后，正常默认配置也达到约 117fps。

操作者明确选择：**正常运行遵循系统省电策略，流畅度测试切换到平衡模式**。
不把诊断中的解除限制变成默认行为。正常交互窗口再次打开后，操作者确认：
“明显顺滑，可以通过本轮交互验收”。按钮、列表、主题切换在默认 125% 缩放下通过。
该轮人工验收时系统为 `performance`。

约 117–126fps 仍低于面板 240Hz。这里确认的是主要卡顿原因与主观交互验收，
没有宣称 240Hz 实际呈现、所有涟漪逐帧质量或整机性能预算已经通过。

## 2. 可重复诊断入口

新增 `crates/mail-ui/src/perf_probe.rs`，使用锁定版本自带的帧记录器，无新增依赖。
通过 `QINGMAIL_PERF_PROBE` 显式启用，预热 1 秒、采样约 5 秒、输出统计并自动退出：

| 值 | 工作负载 |
| --- | --- |
| `frames` | 移动方块，用绘制阶段 `request_animation_frame` 产生连续帧需求，不使用主题 pump |
| `theme` | 约每 200ms 重定向明暗主题，复用正常窗口的单一 pump |
| `idle` | 不制造动画需求，观察静止重绘；本轮关闭 HUD |

输出绘制耗时、平台提交调用耗时、提交间隔、帧信号至绘制启动延迟的均值/P50/P95/最大值，
并记录窗口尺寸、缩放、焦点、电源、减少动态效果与温度状态。每 50ms 收集一次记录，
不通过收集定时器主动请求重绘；静止对照确认该入口本身不持续驱动绘制。
焦点/电源/减少动态效果变化另行输出；按收集时刻分秒计数用于辅助检查静止状态。

`QINGMAIL_PERF_UNTHROTTLED=1` 仅在有效诊断模式中取消窗口的省电帧率限制；
不会关闭失焦或高温限制，不改变系统电源设置；单独设置此变量对普通窗口无效。

```sh
# 先通过桌面电源设置选择平衡模式；该命令本身不切换电源模式。
WAYLAND_DISPLAY=wayland-1 QINGMAIL_PERF_PROBE=theme \
  VK_DRIVER_FILES=/usr/share/vulkan/icd.d/intel_icd.json ./target/release/mail-ui

# 保持系统省电模式，仅诊断窗口取消省电限帧。
WAYLAND_DISPLAY=wayland-1 QINGMAIL_PERF_PROBE=theme QINGMAIL_PERF_UNTHROTTLED=1 \
  VK_DRIVER_FILES=/usr/share/vulkan/icd.d/intel_icd.json ./target/release/mail-ui
```

这些计时使用应用提交完成时间，不是合成器呈现反馈；HUD 的口径同报告 003。
GPU 工作仍可能异步进行，`submit_ms` 也不能被当作纯 GPU 执行耗时。

## 3. 实测条件与结果

Arch Linux；Rust 1.100.0；Hyprland 0.57.2；Mesa/vulkan-intel 26.2.7；
NVIDIA 620.70.06；eDP-1 2560×1600@240Hz、scale 1.25、VRR off。
所有采样窗口为原生 Wayland，平铺尺寸 998×1206 逻辑像素。
Intel ICD 对应仅打开 `/dev/dri/renderD128`；NVIDIA ICD 还打开 renderD129 和 NVIDIA 设备。
两条路径共用 Intel 合成器。HUD 均关闭，`reduce_motion=false`，温度 `Nominal`。

| 构建 / GPU / 负载 | 系统模式 / 窗口策略 | 提交次数 / 秒数 | 提交帧率 | 绘制均值 / P95 | 提交间隔均值 / P95 |
| --- | --- | --- | --- | --- | --- |
| release / Intel / theme | 省电 / 默认 | 141 / 5.002 | 28.19fps | 2.197 / 2.883ms | 35.197 / 42.723ms |
| release / Intel / theme | 省电 / 仅诊断解除限制 | 592 / 5.017 | 117.99fps | 2.039 / 2.698ms | 8.478 / 9.414ms |
| release / Intel / theme | 平衡 / 默认 | 587 / 5.028 | 116.75fps | 2.078 / 2.808ms | 8.566 / 11.297ms |
| release / NVIDIA / theme | 平衡 / 默认 | 630 / 5.005 | 125.89fps | 1.863 / 2.361ms | 7.945 / 9.217ms |
| debug / Intel / frames | 平衡 / 默认 | 239 / 5.046 | 47.36fps | 12.643 / 17.390ms | 21.121 / 26.801ms |
| release / Intel / idle | 平衡 / 默认 | 0 / 5.044 | 无帧需求 | 无样本 | 无样本 |

原始记录：

- [省电与诊断解除限制矩阵](evidence/P0-004-frame-probes.txt)
- [平衡模式默认策略矩阵](evidence/P0-004-balanced-probes.txt)

这是每项单次、约 5 秒的定位采样，不能据此给 GPU 做稳定性能排名。
NVIDIA 跨 GPU 路径在本轮没有表现出比 Intel 更低的主题提交帧率；跨 GPU 不是已确认的主因。
debug 绘制成本明显高于 release；其帧率不能代表发布版本体验。

证据中的非主结论样本也保留：第一组 Intel 无限制 `frames` 起始电源状态曾为 Balanced，
第一组 debug 起始失焦；第二组 Intel `frames` 在 4.448 秒失焦。这些不作为严格受控帧率对比。
第一组 idle 仍有少量绘制，不能判定为空闲通过；第二组平衡模式 idle 的 5 秒采样为 0 次绘制。

首次诊断读取系统为 `power-saver`。平衡模式测试脚本在启动时读取到原模式为
`performance`，临时切到 `balanced`，结束后恢复它实际读取的 `performance`，原始记录末尾有确认。
不根据较早观测覆盖测试开始时的系统状态。

## 4. 源码核对

- `gpui-pre 0.3.12` 的 `WindowOptions::default()` 将
  `low_power_frame_interval` 和 `inactive_frame_interval` 都设为 33.333ms。
  Linux 电源监听将系统 `power-saver` 映射为 `PowerMode::LowPower`；
  `minimum_frame_interval` 选择适用限制的最大值。240Hz 面板不会自动绕过它。
- Material `ButtonRipple` 使用 Base 的 `animate_keyframes` 和 `transition`；
  Base 在动画运行时自行请求下一帧，不需要应用为涟漪另加 pump。
- 本应用未设置 `reduce_motion`；采样中为 false。主题 pump 保留报告 002 的
  单链/无实体重入/事件回调只使用 `on_next_frame` 三条约束。
- 连续绘制对照和主题动画均受省电策略影响，证据不支持“仅主题 pump 少调帧”的判断。
- 该 Wayland 后端的重试定时器为 16.667ms；省电限帧后的实际间隔可超过 33.333ms。
  不能把其与合成器回调共同作用下的约 25–29fps，简单认定为渲染能力不足。
