## 1. 草稿与附件

数据库升级到 schema v2，加入对象索引、多草稿、附件元数据与关联、发送任务及任务附件关联。邮件正文和附件文件在数据目录下 `objects/`，使用随机受控 ID，不将前台路径或附件名作为存储路径。

草稿保存收件人 To/Cc/Bcc、主题、现有受控富文本 JSON 和附件 ID 顺序；正文沿用 mail-content 验证器，不保存任意 HTML。账号隔离，草稿枚举/读取/保存/明确丢弃使用稳定 ID。保存携带期望版本，迟到的自动保存返回冲突，不能覆盖新版本。正文与属性、中文/emoji、完整头部及附件引用均可往返恢复。

附件从后台已经打开的 reader 导入，独占创建 0600 文件；对象目录 0700。文件与目录同步完成后才允许数据库关联。保存 SHA-256 和实际大小，读取、提交前校验完整性并拒绝软链接/硬链接或其他非法文件。失败导入清除未完成对象；数据库提交报错时，只有确认无关联记录才删除文件，避免提交结果不确定时误删已持久化内容。

暂设单附件及附件合计上限 25 MiB、每封最多 32 个；这是本地实现边界，尚未协商 SMTP SIZE，也不代表服务端接受同样大小。正文仍为 P0 模型的 32 KiB、JSON 8 MiB 上限。收件人最多 100 个；编辑中允许不完整地址保存，提交前只允许基础独立 mailbox。完整 RFC 地址解析和 MIME 编码仍须协议构建层验证。主题/地址控制字符和附件名路径片段拒绝。

不可变正文对象采用“文件先同步、数据库后关联”。进程在中间退出可能留下孤立文件，但不产生指向尚未保存文件的成功记录。尚未实现孤立对象回收、缓存预算或旧版本对象清理；保守保留，避免误删任务引用。长期使用仍需受控回收，不宣称已有无限量长期存储管理能力；具体阶段按主基线 §9 的 P3 缓存完善执行，不另加 P2 缓存系统。

## 2. 发送状态与恢复

明确发送动作调用 enqueue_draft，先读取已保存版本、校验附件，再事务保存发送快照和附件关联。同一草稿版本双击返回同一初始任务。任务快照与草稿独立，之后编辑/丢弃草稿不改变既有发送内容。发件人、收件人、主题、正文、附件、创建时间和由任务 ID 推导的 Message-ID 保持稳定。明确重发创建新任务与新 Message-ID，并留旧任务关系。

| 操作 / 恢复点 | 本地结果 |
| --- | --- |
| 只保存草稿 | 不创建发送任务，恢复网络或重启不会发送 |
| 明确发送后入队 | 待提交，完整快照和附件引用已持久化 |
| begin_smtp | 校验完整快照，先持久化正在发送，再返回不可克隆的提交许可 |
| SMTP 明确接受 | 已发副本待保存，之后无法再次取得 SMTP 提交许可 |
| SMTP 明确拒绝 | 明确失败，不自动重试 |
| SMTP 结果无法确认 | 结果不确定，不自动重发 |
| 副本保存失败 / 成功 | 保持已发副本待保存 / 发送成功 |
| 重启发现待提交 | 明确失败，代码 interrupted_before_submission；须用户再次决定 |
| 重启发现正在发送 | 结果不确定，代码 interrupted_during_submission |
| 重启发现已发副本待保存 | 保持，只允许读取副本快照和保存副本 |

重发接口要求调用方传入明确用户确认，且仅接受明确失败/结果不确定；保留原任务状态。对同一旧任务重复确认返回同一个重发子任务，防止重复点击创建多个提交。取消待提交只标记未提交失败；停止处理不确定任务保持“不确定”，不宣称撤回。

状态改动全部采用期望状态约束。不能从发送成功、已发副本待保存或不确定直接回到可发送状态。提交许可在数据库成功保存 Sending 后才返回，消费后记录 SMTP 结果。原始服务器错误响应不进入持久化 detail，仅存固定诊断代码。

这些是给未来后台/协议层的内部 API，不是网络实现或权限系统；调用方仍须按 UI 授权、在线状态和协议确定性正确使用。当前没有任何自动发送扫描器。SMTP 接受但结果未能持久化的崩溃恢复会保守归为不确定，不能据此宣称投递恰好一次。

## 3. 迁移与兼容

v1→v2 升级前生成 SQLite 备份并同步，事务创建新表和设置版本；失败回滚并保留备份。v0 新库同一事务初始化 v1/v2。旧账号和邮件表不重建、不覆盖；测试用真实 v1 结构及账号行验证保留。原 P2-001 v0 初始化的失败回滚测试继续通过。

新增直接依赖为现有 mail-content、serde_json，以及精确指定 `sha2 =0.10.9`（原锁文件已存在）。Cargo.lock 仅增加 mail-storage 依赖边，没有升级任何现有包或 UI 依赖。

并发子进程验证暴露 fork→exec 期间 CLOEXEC fd 可能短暂保持写锁：存储锁增加最多 100ms、每 5ms 的有界等待，持久占用仍报错，不引入后台轮询。

## 4. 验证

在 P2-001 的 9 个存储测试上新增 13 项，共 22 项存储测试：

- 多草稿、中文/emoji/格式与头部恢复、版本冲突、跨账号/重复附件拒绝。
- 发送快照冻结、草稿删除后附件保护、相同版本双击幂等。
- 六状态关键约束、显式重发新 ID、取消/停止处理语义、副本失败只补存。
- 重启待提交暂停、正在发送转不确定、离线草稿不进入队列。
- 两个真实子进程中断点：持久化 Sending 后直接退出；记录 SMTP Accepted 后直接退出。重新打开分别只恢复不确定、只允许副本保存。SMTP 结果为合成事件，没有真实服务器连接。
- 附件同长度内容篡改、软链接、正文损坏拦截且保留原数据。
- 超限与 reader 中途报错不会留下部分对象。
- 目录不可写时保存/入队失败，最后保存版本保留，无法获取提交许可。
- v1→v2 正常升级、故障注入失败回滚、备份可读且旧账号保留。

门禁：fmt/check/test/clippy 全通过；全项目 42 个 Rust 测试通过，release mail-ui build 通过。既有 stub manifest 提示本轮输出 4 条，无新增 Rust/clippy 警告。界面未改动，无需重复原型窗口人工验收。
