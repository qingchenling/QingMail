# P3-007 缓存管理与阶段收口

日期：2026-11-18。基线：P3-006 `46c7622`。本轮交付缓存管理、迁移、集中测试和双二进制测试包；真实双账号及独立第二客户端兼容尚待补验收，P3最终退出条件不能标为全部通过。

## 实现与复用

| 项目 | 实际行为 |
| --- | --- |
| 预算 | schema17 `cache_settings`持久保存，默认1GiB，IPC上限1TiB；现有设置窗口提供256MiB/1GiB/4GiB与刷新用量、二次确认清理。 |
| 引用保护 | `protected_objects`复用既有对象/草稿/附件/发送/服务器原件/上传/离线操作关联。用户导入附件、草稿、发送快照、服务器原件和固定上传快照全部保守保护；非applied操作所引用邮件缓存也受保护。没有另建一套业务对象。 |
| 淘汰 | `cache_access`记录完整正文和分段缓存的访问时间；完整性校验成功才更新。后台Store单写者按访问时间/稳定ID淘汰可下载对象，事务先移除资源引用，再移除文件；邮件索引与MIME清单保留。 |
| 执行时机 | 启动恢复/迁移后、完整正文/分段写入后、调整预算/显式清理及60秒周期维护。受保护内容超预算不删除用户内容，设置显示提示。 |
| 下载安全 | 网络流仍进入匿名临时文件；未完成、失败及取消不发布缓存。完整附件保存时先获取校验后的读取句柄再淘汰，预算为零仍可完成当前导出；已打开fd在Unix unlink后可继续读取，释放句柄后回收。 |
| 失效与恢复 | 淘汰后读取重新走现有按需下载；凭据不可用时说明“未缓存，需要联网下载”。启动仅回收合法受控ID且数据库无记录的孤儿文件，不触碰未知名称。 |
| IPC | CacheStatus/SetCacheBudget/ClearCache接入现有能力表、类型化结果和持久幂等请求；写入成功推进快照版本。正在下载字节由资源状态汇总，普通数据库不持有网络临时内容。 |

预算统计为数据库对象总量（可淘汰与受保护）；不包含数据库/迁移备份/索引、独立浏览器副本、匿名临时下载及已经unlink但仍打开的fd。用户附件和历史固定上传原件采取保守保留，可能超过预算，不能将此预算描述为整个数据目录硬上限。浏览器副本继续使用阅读器的独立清理入口。

## 迁移与恢复

schema8～16顺序迁移到17，沿用迁移前私有SQLite备份、事务迁移和未来版本拒绝。增加缓存偏好、访问记录/触发器及保护视图，不修改密钥库关联、草稿模型或发送许可。schema16迁移测试验证既有正文可读及备份存在；历史schema夹具同步移除17新增项再构造旧库。

清理事务失败时引用与文件均保留；模拟数据库删除中断的测试证明回滚路径。尚未做真实磁盘写满的系统验收，不能将事务故障注入说成真实磁盘满通过。保护超预算、零预算、索引保留、重启恢复和孤儿回收均有相关测试。

## 真实账号兼容

用户授权使用现有账号，仅收信与草稿，不发送邮件。检查发现默认数据目录只有1个账号（升级前schema10）；用户确认第二个账号稍后添加。真实Secret Service读取、目录与INBOX同步、59封索引、选信安全阅读通过。服务器未返回唯一Drafts特殊用途目录，经用户明确确认选择已有 `Drafts`。

测试创建一份带 `QingMail P3-007 compatibility` 标识的草稿；保留供用户检查。实际服务商出现两个兼容差异：新增 `X-QQ-mid` 追踪头，以及Message-ID搜索漏报。实现仅允许新增单个该追踪头，其余原始头/正文逐字节一致，并以服务器实际原件建立共同基线；其他修改或重复追踪头仍拒绝。APPENDUID只是候选，必须重新读取并核验。未知上传仍只查询，搜索漏报时最多读取最新200份Message-ID头（UID集合≤10000、头部总量≤1MiB），唯一候选再读取原件核验，查不到保持不确定。不会重放APPEND，不涉及SMTP路径。

修复后使用同一测试草稿ID与原固定上传请求恢复，不再APPEND；状态已变为synced，独立IMAP重取返回同一原件ID，发送任务保持不变，单账号本轮验收通过。证据见 [真实账号证据](evidence/P3-007-real-accounts.json)。真实独立第二客户端编辑/删除/冲突、第二账号、真实断网/磁盘满综合流程尚待补验收。测试脚本允许继续查询原草稿ID，避免每次排障创建新草稿。
