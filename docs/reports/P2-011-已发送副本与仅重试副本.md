# P2-011 · 已发送副本与仅重试副本

> 历史轮次记录：下文“当前/尚未”均指本轮结束时；最新实现与待办以 [P2 当前状态与剩余工作](../P2-当前状态与剩余工作.md) 为准。

- 日期：2026-11-16
- 状态：实现、105 个 Rust 测试与构建门禁通过；副本协议用本机 TLS 假服务器验证，真实服务商与真实投递未验收。

## 1. 本轮范围

只补齐发送闭环的“已发送副本”一段：SMTP 已被接受后，把同一份冻结 MIME 保存到 IMAP 已发送文件夹；保存成功才把任务标为 Sent；保存失败或结果不确定保持 CopyPending，并提供“只重试副本”的入口。没有实现受控重发、停止处理、独立任务页面，也没有改动 SMTP 提交语义。

复用既有 `send_tasks` 状态机与冻结快照，不重做 `begin_copy/finish_copy` 之外的存储设计，不自动重发，不新增依赖，SQLite 从 schema5 升到 schema6。

## 2. 实现

### 2.1 协议层：已发送文件夹定位与 APPEND

新增 `crates/mail-service/src/sent.rs`，一次 IMAP 连接内完成：

1. `LIST "" "*"` 取得可选文件夹。优先沿用任务上次记录的文件夹；否则按叶子名（识别服务器分隔符，名称先按 modified UTF-7 解码）选择常见“已发送”名称，如 `Sent`、`Sent Items`、`Sent Mail`、`已发送`、`已发送邮件`；忽略 `NoSelect` 节点。找不到时返回 `copy_no_sent_folder`，不猜测、不创建文件夹。
2. `EXAMINE` 已发送文件夹并核对 UIDVALIDITY。
3. 追加前先 `UID SEARCH HEADER Message-ID "<冻结值>"` 查重。命中则直接按“已存在”处理，不再 APPEND；查重失败时同样不追加，避免重复副本。
4. 同步字面量 `APPEND "文件夹" (\Seen) {长度}`：等待服务器 `+` 继续后才发送正文字节，正文即发送构建层产出的同一份 MIME（确定性重建，Date/Message-ID/boundary 均冻结）。
5. 读取 tagged 结果：`OK` 记录 `APPENDUID` 的 UIDVALIDITY/UID；服务器未提供 UIDPLUS 时 UID 记为未知，不伪造。

错误分类写入固定脱敏代码，不含密码或服务器原文：

| 情况 | 代码 | 任务状态 |
| --- | --- | --- |
| 没有可用已发送文件夹 | `copy_no_sent_folder` | CopyPending |
| 认证/TLS/连接/超时/协议/上限 | `copy_auth_failed` 等 | CopyPending |
| 查重失败 | `copy_search_failed` | CopyPending |
| 服务器明确拒绝 APPEND | `copy_append_rejected` | CopyPending |
| 正文字节已发出后连接中断 | `copy_result_unknown` | CopyPending，重试前先查重 |

“正文前”的失败是明确未保存；“正文后”任何无法确认的分支都保守标为不确定，绝不在同一轮内盲目重试。

### 2.2 存储层：副本位置与结果

`send_tasks` 增加 `copy_folder/copy_uidvalidity/copy_uid`（schema-v6 迁移，旧库先备份）。`SendTask` 暴露 `copy: Option<SentCopy>`。

- `copy_ready` 只在 CopyPending 时返回冻结快照、上次副本文件夹与 IMAP 配置。
- `finish_copy` 区分 `Saved`、`Failed`、`Uncertain`：只有 `Saved` 原子地进入 Sent；其余保持 CopyPending 并只写固定诊断代码；未知代码被拒绝。
- `copy_pending_tasks` 提供待保存副本的任务列表，不联网、不自动触发。
- 重启恢复逻辑不变：`copy_pending` 原样保留，`sending` 仍恢复为不确定，`pending` 仍恢复为失败。

### 2.3 协调与界面

发送线程在 SMTP 返回“接受”并写回 CopyPending 后，继续用冻结快照重建 MIME 并执行副本保存，最终返回 Sent 或带原因的 CopyPending。该阶段仍受全局单任务互斥和退出等待约束，因此退出不会丢结果。

写信窗口的发送记录：

- CopyPending 持续显示状态与可操作原因（如未找到已发送文件夹、认证失败、查重失败、结果未知）。
- 每个 CopyPending 任务出现“重试保存副本”。点击后只调用 `SendCoordinator::retry_copy`，只走 IMAP 副本并先查重；不经过 SMTP，不创建新任务。
- Sent 且查重命中时显示“服务器上已有同一副本，未重复保存”。

## 3. 验证

- [全量 105 个 Rust 测试通过](evidence/P2-011-tests.log)（P2-010 为 93 个）。新增 12 个：
  - 协议 7 个：文件夹选择确定性/忽略 NoSelect；APPEND 写出的字节与冻结 MIME 完全一致并解析 APPENDUID；查重命中后不再 APPEND；无已发送文件夹时不 EXAMINE/APPEND；服务器拒绝 APPEND 与查重失败；正文发送后断线标为不确定；无效标识或超限字节不建立连接。
  - 存储 2 个：只有确认保存才进入 Sent，失败/不确定保持可重试且拒绝未知诊断代码；v5→v6 迁移保留 CopyPending 任务。
  - 协调 3 个：副本失败后任务仍为 CopyPending，重试只保存副本且不增加 SMTP 调用；不确定结果重试时按查重命中记为已存在；已有副本的任务拒绝再次重试。
- fmt --check、workspace 全目标 check --locked、clippy `-D warnings`、release 构建通过；仅保留既有 mail-protocol stub manifest 提示。
- 协议测试使用本机 TLS 假服务器脚本化 LIST/EXAMINE/SEARCH/APPEND；协调测试注入 Fake Vault 与模拟副本结果，不访问 Secret Service。写信窗口的“重试保存副本”按钮由编译与协调测试覆盖，本轮没有单独的按钮点击原生探针。

没有使用真实凭据、没有连接真实邮箱、没有发送邮件。真实服务商的已发送文件夹命名、`SEARCH HEADER` 与 `APPEND` 行为、APPENDUID 支持仍待集中验收。

## 4. 限制与下一轮

- 副本保存失败后的“修改/重发”、不确定后的“查看已发送/二次确认重发/停止处理”尚未接入；存储层 `resend_task/stop_uncertain` 保留，但产品入口和网络流程未实现。当前有发送记录的草稿仍一律禁止再次提交。
- 没有独立发送任务页面；任务与原因只在写信窗口可见。
- DNS、整次 SMTP 提交与整次副本保存仍无独立总期限，慢网络下“保存并退出”仍可能长时间等待；本轮未做强制取消。
- 副本文件夹靠名称启发式定位；若服务器使用非常规名称，需用户后续在账号管理中显式指定（尚未实现）。
- 真实账号贯通、持续使用与无重复发送证据仍待操作者授权后集中验收。

下一轮建议实现受控重发/停止处理与故障详情入口，然后回到回复/转发与产品整合。
