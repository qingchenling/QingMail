# ADR-0003：P0–P2 单进程运行，P3 拆分 daemon 与 IPC

- 状态：已接受
- 日期：2026-11-16
- 关联：主文档 §3、§9、§10.3

## 背景

目标架构是 GPUI 前台 + 独立 Rust 后台进程，通过当前用户专用的 Unix socket（逐行 JSON，带版本、请求 ID 和消息类型）通信，以支撑托盘、通知和关窗后的后台常驻同步。

但从第一天起实现并冻结 IPC 协议的代价是：P0/P2 阶段接口必然反复变动，协议版本协商、进程生命周期、崩溃恢复都是额外的工程量，且在单账号闭环验证完成前缺乏稳定依据。

## 决策

1. P0–P2：后台逻辑（同步、发送、存储、内容处理）与前台在同一进程内运行，仅按模块边界（crate）隔离，依赖方向不变。生命周期语义等效实现：关闭主窗口保持进程与同步运行，托盘可用时提供"打开/退出"入口。
2. P2 结束、内部接口稳定后，将内部 API 冻结为 IPC 协议 v1，随后在 P3 执行进程拆分：daemon 独立进程、Unix socket 通信、实例锁、单实例语义。
3. 拆分的验收标准：拆分后行为与单进程阶段一致（关窗常驻、重启复用、明确退出），同步与发送状态无丢失、无重复发送。
4. 共享代码（mail-core、mail-protocol、mail-content、mail-storage、mail-service）从第一天就按未来拆分的边界组织，拆分时不重构领域逻辑。

## 后果

- P0/P2 的验证与迭代速度显著提高，协议设计建立在真实使用流程之上。
- 引入一次 P3 阶段的有计划迁移；以阶段退出条件约束，不允许拆分引入行为差异。
- P0–P2 期间"前台退出后后台仍在"等测试项以进程内等效行为验证，完整验证推迟到 P3。
- 生命周期细节（无托盘宿主降级、第二实例处理）在 P3 落地，主文档 §3.2、§3.3 的完整要求自拆分起生效。
